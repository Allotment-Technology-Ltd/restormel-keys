# Changelog

Single record of meaningful repo changes.

## Unreleased

### Added

- **Developer portal SSO with dashboard (Neon Auth).** `/keys/auth/authorize` detects an existing Neon Auth session on `restormel.dev` and issues the portal OIDC JWT without sending the user through the separate GitHub OAuth app. Unauthenticated users still use `PORTAL_GITHUB_*`. `redirect_uri` is allowlisted (Zuplo hosts + optional `PORTAL_ALLOWED_ORIGINS`); callback rejects invalid `redirect_uri`. Runbook: [docs/runbooks/zuplo-developer-portal-go-live.md](docs/runbooks/zuplo-developer-portal-go-live.md).
- **Gateway-key unification for policy evaluate + docs deprecation of Management Key.** `POST /keys/dashboard/api/policies/evaluate` now accepts session and project Gateway Key auth, enforces key project/workspace scope, and rejects deprecated `management_key` auth. Added endpoint tests for unauthenticated, gateway success/scope mismatch, and management-key rejection. Walkthrough guidance (app docs + docs/walkthrough specs) and Access page copy now remove Management Key requirements and standardize on backend Gateway Key usage for policy evaluation.
- **Walkthrough agent prompts and layout unification.** Public walkthrough pages (Phase 0–6, migration-paths, verification-strategy) include an optional "Agent prompt(s)" section: copy-paste prompts for coding agents, collapsed by default; `RESTORMEL_DOCS_AGENT_PROMPTS=false` hides site-wide. Component: `AgentPromptsSection.svelte` with `CodeBlock`; distinct from step accordions. Single header (SiteHeader) and footer (SiteFooter) across the site; GitHub link in footer only. Max-width container `--rm-container-max` (72rem) for docs and dashboard; collapsible side navs for docs and dashboard (state in localStorage). See STATUS.md and ARCHITECTURE.md for current apps/tech state.
- **Dashboard nav refactor (Prompt 12).** Left-nav and information architecture updated to canonical sections: Overview, Projects, Access, Provider Integrations, Models, Routes, Policies, Analytics, Logs & Traces, Lifecycle & Migrations, Billing & Forecasting, Documentation (external), Settings. New route skeleton and placeholder pages for Access, Provider Integrations, Models, Routes, Policies, Analytics, Logs & Traces, Lifecycle & Migrations; existing Overview, Projects (and project detail with Gateway keys/usage), Billing, Settings preserved. Single source for nav and topbar title in `$lib/nav-config.ts`; topbar shows section title from path. Placeholder pages use `PlaceholderPage.svelte` with clear “not fully implemented” copy and links to existing pages where relevant. No fake functionality. Tests: `nav-config.test.ts` for NAV_ITEMS structure and `topbarTitle()`.
- **Policy foundations (Prompt 11).** Policies and policy bindings as first-class backend objects. Neon: `listPolicies`, `getPolicy`, `createPolicy`, `updatePolicy`, `deletePolicy`; `listPolicyBindings`, `listPolicyBindingsByTarget`, `createPolicyBinding`, `deletePolicyBinding`; `evaluatePolicies(context)` returning violations array. Rule shapes: model_allowlist / model_denylist `{ modelIds: string[] }`, provider_allowlist / provider_denylist `{ providerTypes: string[] }`, deprecated_model_block (no config), budget_cap / token_cap `{ limit?: number }` (placeholder). Enforcement: model/provider allowlist/denylist and deprecated_model_block evaluated when modelId, providerType, or modelLifecycleState in context; budget/token not enforced in v1. API: GET/POST `/api/policies`, GET/PATCH/DELETE `/api/policies/[id]`, GET/POST `/api/policies/[id]/bindings`, DELETE `/api/policies/[id]/bindings/[bindingId]`, POST `/api/policies/evaluate` (body: context). Access: same as integrations (session or management_key). Domain: added `model_denylist`, `provider_denylist` to PolicyType. Docs: [docs/reference/policy-enforcement.md](docs/reference/policy-enforcement.md) (enforced now vs later). Tests: policy list, create (validation, success), evaluatePolicies (no violations, with violations).
- **Routes as first-class backend objects (Prompt 10).** Route and RouteStep persistence and CRUD. Neon: `getEnvironmentInProject`, `listRoutes`, `getRoute`, `createRoute`, `updateRoute`, `deleteRoute`, `listRouteSteps`, `createRouteStep`, `updateRouteStep`, `deleteRouteStep`, `getRouteWithSteps`. Route: name, project/environment scope, defaultModelId, billingMode, routeMode, status. Step: orderIndex, providerPreference, modelId, conditionBlock, **fallbackOn** (fallback behaviour), timeoutMs, enabled. API: GET/POST `/api/projects/[id]/routes` (optional ?environmentId), GET/PATCH/DELETE `/api/projects/[id]/routes/[routeId]`, GET/POST `/api/projects/[id]/routes/[routeId]/steps`, PATCH/DELETE `/api/projects/[id]/routes/[routeId]/steps/[stepId]`. Access: same as project (session, gateway_key, management_key). Bridging: [docs/reference/routes-bridging.md](docs/reference/routes-bridging.md) — dashboard Route/RouteStep are not yet used by headless `createRouter`; no change to existing request execution. Tests: route list, create (validation, success), get (404, 200), resolution (getRouteWithSteps).
- **Model catalog backend foundation (Prompt 9).** Read-only catalog: `ModelRecord` and `ProviderModelVariantRecord` in neon; `listModels(filters)` with optional `lifecycleState`, `family`, `limit`, `offset`; `getModel(id)`; `listProviderModelVariants(modelId)`. API: GET `/api/models` (query: lifecycleState, family, limit, offset), GET `/api/models/[id]` (model detail with `variants[]` for frontend). Lifecycle, pricing (via variant pricingRef), and capability fields supported (partially populated). Optional seed migration `005_seed_model_catalog.sql` (gpt-4o, gpt-4o-mini, claude-3-5-sonnet + variants). Tests: catalog listing, filtering (query params, limit clamp), detail (404, model + variants).
- **Provider Integrations backend (Prompt 8).** Workspace-scoped provider records and project/environment bindings. Neon: `listProviderIntegrations`, `getProviderIntegration`, `createProviderIntegration`, `updateProviderIntegration`, `deleteProviderIntegration`, `updateProviderVerification`; `listProviderBindingsByIntegration`, `listProviderBindingsByProject`, `createProviderBinding`, `deleteProviderBinding`. Secure credential storage: only `credential_ref` (no raw secrets). Verification state: `verification_status`, `last_verified_at`; POST `/api/integrations/[id]/verify` placeholder. API: GET/POST `/api/integrations`, GET/PATCH/DELETE `/api/integrations/[id]`, GET/POST `/api/integrations/[id]/bindings`, DELETE `/api/integrations/[id]/bindings/[bindingId]`, GET `/api/integrations/[id]/models` (placeholder), GET `/api/projects/[id]/provider-bindings` for frontend. Audit events on create/update/delete integration and create/delete binding. Access: session or management_key only (gateway_key cannot list integrations). Tests: integrations-auth (workspace/actor resolution), integrations API (list, create, validation).
- **Auth and secret-handling foundations (Prompt 7).** Dashboard accepts **Gateway keys** (Bearer) for programmatic API access: when no session, `Authorization: Bearer <rawKey>` is verified via SHA-256 hash lookup in `api_keys`; `last_used_at` updated on use. **Management keys** (Bearer) verified via `management_keys` table; workspace-scoped (list projects in workspace, get/update/delete project in workspace, keys for those projects). Scoped access: Gateway key restricted to its project; Management key to its workspace; session unchanged. New: `verifyGatewayKey`, `verifyManagementKey`, `listProjectsByWorkspace`, `getProjectInWorkspace` in neon; Bearer resolution in `hooks.server.ts`; `getBearerToken` in `$lib/server/bearer` (tested). Billing checkout and project create require session (key auth returns 403). No raw keys logged; provider credentials remain separate (credential_ref only).
- **Control-plane schema (migration 004).** New tables: management_keys, provider_integrations, provider_bindings, models, provider_model_variants, routes, route_steps, policies, policy_bindings, audit_events, request_logs, usage_aggregates. Optional columns on api_keys (name, scope, status, created_by, last_used_at, expires_at, rotation_version). Audit events written on Gateway key create/revoke; other tables are phased groundwork. Secrets: provider_integrations.credential_ref only (no raw credentials). Rollback and notes in [docs/reference/control-plane-schema-004.md](docs/reference/control-plane-schema-004.md).
- **Workspace / Project / Environment hierarchy.** Migration `003_workspaces_and_environments.sql`: `workspaces` table (one per user), `workspace_id` on `projects`, `environments` table (dev/prod per project). Backfill: one default workspace per existing user, link projects to it; seed dev and prod environments for existing and new projects. Dashboard: `getOrCreateDefaultWorkspace`, `listEnvironments`; project detail page shows Environments section. Ownership remains `user_id`; workspace groups projects for future multi-tenant use.
- **Canonical domain models (@restormel/keys).** New `packages/core/src/domain.ts` with types: Workspace, Project, Environment, GatewayKey, ManagementKey, ProviderIntegration, ProviderBinding, Model, ProviderModelVariant, Route, RouteStep, Policy, PolicyBinding, RequestLog, UsageAggregate, AuditEvent, CustomerTenant, ExposureRule, PricingRecord, RateLimitRecord, LifecycleEvent. Exported from `@restormel/keys`. Only Project and GatewayKey are currently persisted (dashboard); others are placeholders until wired. Mapping and persistence notes in [docs/reference/domain-models.md](docs/reference/domain-models.md).
- **Key taxonomy refactor (Gateway Key vs Provider credential).** User-facing copy and docs now use precise terms: **Gateway Key** for Restormel auth (keys created in the dashboard, format `rk_...`); **Provider credential** for upstream provider secrets (e.g. OpenAI API key) in embeddables and demos. Dashboard: all “API key” copy → “Gateway key” (section titles, buttons, empty states, confirmations). Runbooks (zuplo-setup, zuplo-launch-cli): “backend API key” → “backend Gateway key”. UX contracts and documentation-strategy: canonical term “Gateway key”. Demo Next.js settings: heading “API keys” → “Provider credentials”; ModelSelector unavailable reason “No API key” → “No provider credential”. API: `GET/POST /api/projects/[id]/keys` responses now include optional `type: "gateway"` for clarity; no breaking change to `keyPrefix` or `rawKey`. Table name `api_keys` and env var `KEYS_BACKEND_API_KEY` unchanged. See [restormel-minimum-viable-refactor-path.md](docs/reference/restormel-minimum-viable-refactor-path.md).

### Removed

- **GCP load balancer (Phase 3).** Pulumi infra no longer provisions the global HTTPS load balancer, static IP, serverless NEG, managed SSL cert, URL map, or forwarding rules. restormel.dev is served by a Cloudflare Worker; dashboard is reached via direct Cloud Run URL or Worker proxy. Exports `loadBalancerIp`, `loadBalancerHttpsRule`, `managedCertificateName`, `dnsRecordsForVercel` removed. Runbook `docs/domain-mapping-restormel-dev.md` marked superseded.
