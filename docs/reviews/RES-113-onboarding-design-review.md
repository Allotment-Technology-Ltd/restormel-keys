# RES-113 — onboarding & core-navigation design handoff: feasibility & reconciliation review

> **Ticket:** RES-113 — https://huly.allotmentology.tech/workbench/allotment-pm/tracker/RES-113
> **Status of this document:** review + decision-capture only — **no code was changed and nothing was implemented.** It gates the RES-113 build; resolve the open questions before writing code.
> **Source under review:** the design handoff bundle `docs/design/onboarding-handoff/` (treated as *intent, not implementation*).
>
> **Founder steer (2026-06-27):** the Claude Design handoff is the **hard-won, iterative direction of travel for the product — stick as close to it as possible.** This *resolves the gating question below in favour of the design.* Where the live code and the handoff diverge, **the handoff wins as intent**, and the divergences in this review are the **migration map** to it — realised through Svelte + our token layer + the existing backend machinery, *not* a literal React port (`08_ARTEFACTS.md`: keep the intent, adapt the mechanic). The earlier shipped "Phase 3 north-star" IA is **superseded by this direction** where they differ, so rewriting its test-locked contracts is *expected migration work*, not a blocker. The honest risks below (trust/EBV, M3/M4 backend gaps) still stand — they bound *how faithfully* each screen can ship today, not *whether* to pursue the design.

## Context

This reviews the **Restormel onboarding & core-navigation design handoff** (`docs/design/onboarding-handoff/`) against the live `apps/dashboard` codebase, as the gate before any RES-113 build. The handoff is a complete hi-fi design session output — concept (`01_CONCEPT.md`), IA (`02_IA_AND_NAV.md`), per-screen specs (`03_SCREENS.md`), tokens (`04_TOKENS.md`), state model (`05_STATE.md`), a React→Svelte guide (`06_SVELTE.md`), paste-ready build prompts (`07_PROMPTS.md`), and an artefact map (`08_ARTEFACTS.md`), plus a clickable React/HTML prototype. Per `README.md` §0 and `08_ARTEFACTS.md`, the `designs/` files are **intent, not implementation** — they were built in React/HTML for speed and are to be recreated as Svelte against our existing tokens and components. The handoff itself flags (`README.md` §3) that its codebase observations are "a snapshot, not gospel" and asks the dev to confirm structure first. That confirmation is the central result of this review: the structure has moved on. Evidence below is drawn from seven subsystem investigations against the canonical read-only checkout at `/Users/adamboon/projects/restormel-keys-wt-res113`; every codebase claim carries a `path:line` citation. This review should be read alongside the in-train RES-113 spine proposal (`docs/design/connect-pipeline-ux-review-2026-06-19.md`), which maps the same Connect→Ingest→Make-Ready→Review→Go-Live territory from the existing-code side; the Verdict and Conflicts sections below reconcile the handoff’s M0–M4 journey against it.

## Verdict & scope recommendation

**Plan A is confirmed as the MVP; Plan B (Autopilot) is confirmed out-of-scope as a documented north-star.** This matches the handoff's own framing (`README.md` §0, `01_CONCEPT.md` §7, `07_PROMPTS.md` "do not build Plan B") and nothing in the codebase argues against it. The five-aha journey (M0 Explore → M1 Build → M2 Verify → M3 Store → M4 Connect) with the mandatory M0→M1→M4 spine and a persistent home is the right thing to ship to test the market, and Autopilot's "brief an operator, system runs the spine" model is correctly deferred on complexity grounds.

**The direction is settled; this is a migration onto live machinery, not a from-scratch build — and not yet buildable *faithfully* on every screen.** The dominant finding across all seven subsystems is **divergence, not absence**: the handoff **supersedes the already-shipped "Phase 3 Stage 6 north-star redesign"** (founder steer, 2026-06-27 — the design is the direction of travel), whose primary nav is *Answer Console · Sources · Traces · Keys & Routing* with Operator/Foundation/Observe collapsed groups, and which had **deliberately rejected the verb spine, dissolved the Connect hub, and demoted the operator desk** — a position locked in code and tests (`apps/dashboard/src/lib/nav-config.ts:1-11,72-77`; `apps/dashboard/src/lib/nav-config.test.ts:37`; header comment "The Connect hub stays dissolved — sections are intents"). The handoff's IA (Home · Build · Verify · Connect) reverses that, and adopting it means deliberately rewriting those test-locked contracts as planned migration work. Crucially, this is good news for cost: roughly 80% of the surfaces the handoff wants already exist under different names and locations and are **reusable substrate to move toward the design** — the milestone spine itself is shipped as a server-derived 5-stage Connect spine (`apps/dashboard/src/lib/connect/connect-spine.ts:29`), M0 as the Answer Console + `FirstRunStrip` on a seeded demo graph, M1 as a production-grade ~2,170-line ingest run console, M2 as the Claims stamping desk + trust scorecard, and M4 as the split `/integrations`, `/agents`, `/access` sections. No onboarding code has started (`feat/res-113-onboarding-records` sits at main `3c381163`), so adopting the design is a clean forward migration onto that machinery, not a code rollback.

**The gating question is resolved (founder steer, 2026-06-27): the design is the direction — stick close to it.** The earlier fork ("does RES-113 *supersede* the shipped north-star IA, or *layer* on top?") is settled in favour of **supersede toward the design**. The posture is therefore **reshape-toward-the-design, maximising reuse**: realise the handoff's pedagogy (the five ahas, the one-next-action rail, the honest states, the copy, the M0–M4 / Build·Verify·Connect IA) by **wiring it onto the existing server-derived spine, trust scorecard, run console and stamping desk** rather than rebuilding them, and **deliberately rewrite the test-locked IA contracts** (`nav-config.test.ts`, the route manifest, the 308 redirects) as one planned IA migration. Two pieces are genuinely new and backend-first — **M3 Store** (own-DB move) and **M4's typed-connection-with-access-level model** — carved out as their own scoped, security-reviewed builds because they have no backend today. What still needs a product answer before the *affected screens ship faithfully* is narrower than the direction: the **trust-meter / EBV honesty** question (can a "production-grade" badge ride on today's structural score, or is it blocked on evidence-bound verification?) and the **M3/M4 backend scope** — see Open Questions. Everywhere else, build toward the mocks.

## Strengths worth preserving

The design intent is strong and, tellingly, much of it is already what the codebase converged on independently — which is the best possible signal that the thinking is sound. Preserve:

- **The five ahas as the organising spine.** Sequencing realisations, not features ("it answers from real sources" → "that's MY knowledge" → "I can trust it" → "it runs on MY infra" → "my product can use it"; `01_CONCEPT.md` §2). The codebase already encodes an equivalent ledger (`connect-spine.ts:29`, rendered by `ConnectSpineLedger.svelte`), so the spine concept is validated by reality — only the vocabulary differs.
- **Derive journey position from real state, never a wizard router** (`05_STATE.md` §4-5). The codebase agrees emphatically: the spine is built purely from signals the surfaces already load, with no new queries (`connect-hub-load.ts:230`), and the team explicitly killed the "option-gated client blockers" pattern that "caused the silent-no-op class" (`connect-spine.ts:234`). This intent is a keeper — it just must be honoured server-side, not via a persisted client store.
- **Model-choice-at-ingest, never retroactive** (`01_CONCEPT.md` lesson 1). Honoured in spirit today — routes are chosen before a run (`pipeline-config.ts:103-145`) — and worth protecting as the build reframes the Configure step.
- **Honest states under failure as a product principle, not polish** (`01_CONCEPT.md` lesson 6, `07_PROMPTS.md` notes). The run console already exceeds the mock here (named per-stage failure banners, preflight key-rejection gate, restart, stall/reclaim; `ConnectIngestRunConsole.svelte:856-913`, `run-preflight.ts:114-160`), and the validator now fails *safe* — units the validator omitted default to `weak` and route to remediation rather than slipping in as supported (`packages/connect-core/src/ingest/validation.ts:120-124`). This honesty is the brand; keep it central.
- **Non-destructive, reversible framing for scary actions** (`01_CONCEPT.md` lesson 7). Partially realised already as the additive-only, revocable `allow_claim_versions_table` opt-in ("writes to it but never alters or drops your existing tables"; `ConnectGraphStorePanel.svelte:654-680`) and a true read-only verify handshake (`RETURN true;`, "nothing written"; `graph-target-service.ts:520,562`). Preserve the safety *intent*; reconcile the *mechanic*.
- **"One Connect concept, many shapes," each connection with its own key** (`01_CONCEPT.md` lesson 4) — as a *conceptual* model for serving. (Note: the codebase deliberately went the other way on *nav* placement; see Conflicts.)
- **Ruthless IA discipline** (`01_CONCEPT.md` lesson 9): occasional config does not earn top-level nav. The shipped north-star redesign shares this value exactly — it just cut to a different four. Whichever IA wins, the discipline is right.
- **The neo-brutalist visual system, built entirely on existing tokens.** Token coverage is excellent — every one of the 97 custom properties the mock's stylesheet uses exists with matching values in `packages/keys-tokens/src/brutalist-rm.css` + `base.css`. Zero new tokens are required.

## Gaps & ambiguities needing a product/design decision

These are genuine holes or fork-in-the-road choices the handoff does not resolve:

- **M3 Store (own-DB move) has no backend.** There is no `/store` route and no own-DB *move* surface — only a design doc (`docs/design/tenant-db-provisioning-design.md`) and a module flag `connectNeonGraphStore` (`apps/dashboard/src/lib/module-flags-types.ts:16`). The store *panel* exists, but as a demoted aside of the ingest wizard, and its premise is inverted (see Conflicts). Building M3's "this DB isn't empty → use/add/keep-separate" choice + "switch back anytime" guarantee requires tenant-DB provisioning that does not exist; without it the UI is a stub. **Decide: is M3 in scope now, or deferred?**
- **M4's connection model has no data/auth backing.** The handoff's core M4 entity — a connection bundling a *type* (widget/MCP/REST/SDK/GraphQL) + an *access level* (read vs read+write) + its own key — does not exist. Real keys are flat, project-scoped, label-only, and implicitly read+write (`api/projects/[id]/keys/+server.ts:22,40`; the same auth gates both the read (search) and write (memory) paths with no scope concept, `memory-handler.ts:59`). **Decide: is "access level" an enforced key scope (a security-model change) or a UX label? Is a "connection" a new persisted entity over keys, or relabelled keys?**
- **The "Chat widget (No code)" connection type has no product behind it.** Nothing serves an embeddable answer widget (`FeedbackWidget.svelte` is internal; `/api/embed` is vector infra). **Decide: build the widget, or drop the card until it exists.**
- **The persona model (Initial/Learning/Advanced) has no real source.** No such taxonomy exists in code; the closest concepts are a derived 2-phase `initial|operational` (`connect-journey.ts:67`) and an unrelated, currently-disabled 5-mode `user-mode` store (`stores/user-mode.ts:3`). There is no persona-*inference* mechanism (`07_PROMPTS.md` prompt 1 assumes one). **Decide: which taxonomy is canonical, and how is persona inferred in production?**
- **Default landing is contested.** The handoff treats Home as the every-session hub; reality lands users on the Answer Console (`WORKSPACE_HOME_HREF = /keys/dashboard/prove/proof`, `nav-config.ts:61`) and the dashboard root 308-redirects there. **Decide: Home or Answer Console as the landing.**
- **Two spine vocabularies.** M0–M4 / Build·Verify·Connect vs the shipped `connect·ingest·make_ready·review·go_live`, the latter already wired to `connect_stage_advance` funnel analytics. **Decide which is canonical** — renaming the live spine has analytics + test cost.
- **Trust number semantics.** The mock's `88 + gate-bonus → 97` is a demo device; reality has a weighted structural scorecard that is the single source of truth surfaces must *quote, never recompute* (`trust-score.ts:38`, `trust-scorecard-service.ts:132`). **Confirm the demo numbers are placeholders and the real scorecard drives the meter — and define what counts as "production-grade."**
- **The "44px input floor" the docs promise is not enforced globally.** `04_TOKENS.md` claims inputs already enforce `min-height:44px`; the global `.input` does not (only `.btn` does; `app.css:36-59`). **Decide: add `min-height:44px` to `.input`, or standardise onboarding on `<BrutalInput>`.**

## Conflicts with the current codebase

**Routing — top-level verb spine vs the `/keys/dashboard` namespace (BLOCKER + HIGH).** The handoff (`07_PROMPTS.md` prompt 2; `02_IA_AND_NAV.md` §5) specifies primary nav *Home · Build · Verify · Connect* with route folders `build/ verify/ connect/ settings/*`. The entire app is namespaced under `DASHBOARD_BASE = "/keys/dashboard"` (`apps/dashboard/src/lib/dashboard-base.ts:5`); there are **no** `/build` or `/verify` routes, and the only top-level `/connect` is a module-gate redirect to `/keys`. The shipped primary nav is a different four — *Answer Console · Sources · Traces · Keys & Routing* (`nav-config.ts:72-77`) — chosen by the north-star redesign that explicitly demoted the operator desk and dissolved Connect, and is asserted by `nav-config.test.ts:37`. Honouring the handoff literally means reverting a merged, sign-off-gated redesign and rewriting its tests; introducing `/build /verify /connect` also collides with the 308 legacy-redirect contract (`legacy-route-redirects.ts:50`) and the route-manifest classification gate (`route-manifest.test.ts:48`), failing CI until reclassified. The good news: the nav **is** genuinely config-driven (`WORK_NAV_ITEMS`, `NAV_GROUPS`, `isWorkNavActive`, module-flag filters all centralised in `nav-config.ts`), so a re-spine is a config + test rewrite in one file — but it is a deliberate rewrite, not an additive edit.

**App state — proposed client store vs server-truth (BLOCKER).** `05_STATE.md`/`06_SVELTE.md` prescribe a persisted client `graph.svelte.ts` runes store with an `applyEffect` that *mutates* hardcoded demo numbers (ideas=1204/trust=88→97). Reality derives all of this server-side: the spine is built from real signals (`connect-spine.ts:381`, assembled in `connect-hub-load.ts:230`), and the spine code explicitly warns against the client-blocker pattern that "caused the silent-no-op class" (`connect-spine.ts:234`). A second, client-persisted source of journey truth would drift from the real stores after any server change — re-introducing exactly the bug class the spine was built to kill. Two further frictions: the proposed key `restormel_onboarding` is namespace-adjacent to the existing `restormel_onboarding_complete` flag (`FirstRunOnboarding.svelte:19`), and the app uses **zero** `$state` runes / `.svelte.ts` modules today (all stores are Svelte-4 `writable()`; `stores/user-mode.ts:94`) — a runes store would be the first of its kind (feasible, but a new convention to align on). **Recommendation: derive onboarding position from the existing spine/hub payload; do not persist a graph object.**

**Auth / persona (HIGH).** Covered under Gaps — no persona taxonomy exists, two incumbent and partly-disabled taxonomies collide with it, and there is no inference mechanism (`connect-journey.ts:14`, `stores/user-mode.ts:3`, `FirstRunOnboarding.svelte:21`, which is hard-gated off via `SETUP_ASSISTANT_ENABLED = false`).

**Keys/tokens coverage (mostly GREEN, with named gaps).** At the raw-token level "reuse, don't invent" is fully achievable — all 97 tokens exist with matching values (`brutalist-rm.css:15-94`, `base.css:30-59`). The gaps are at the utility-class/component layer:
- **`.brutal-input` / `.brutal-label` / `.brutal-field` / `.brutal-card` / `.brutal-card-title` are NOT global classes** — they exist only component-scoped inside `BrutalInput.svelte:48-57` and `BrutalCard.svelte:48-59`. Writing `class="brutal-input"` in new markup yields an unstyled element; you must use the `<BrutalInput>` / `<BrutalCard>` components. The handoff (`04_TOKENS.md` §Inputs, mock `designs/styles.css:386-429`) presents them as reusable classes — a literal copy will silently fail.
- **Global `.input` lacks `min-height:44px`** (`app.css:36-59`) despite the docs' a11y claim — a real hit-target gap on every onboarding form built with `.input`.
- **Global `.card` is incomplete** (`brutalist-utilities.css:85-95`): shadow + hover only; border/background appear *only* when nested under `.app-main/.main/.admin-main` (`dashboard-surfaces.css:47-53`), and never get padding. A bare `<div class="card">` renders as a floating shadow. Use `<BrutalCard>`.
- **Filled "state chips"** (run-console done/active/queued, M2 gate statuses) have tokens (`--state-ok/warn/fail-bg/fg`, `brutalist-rm.css:158-163`) but **no class or shared component** — only outline `.status-*` badges (`app.css:284-310`) and hand-rolled inline usage (`IngestQualityCallout.svelte:37-47`). The most state-heavy onboarding screen (M1 run console) has no ready filled-chip primitive.
- **Footgun:** the brutalist values only resolve when `brutalist-rm.css` is the active sheet (imported by `app.css:6`); `base.css`/`semantic-rm.css` resolve the *same names* to a DARK, blurred, IBM-Plex theme — any onboarding surface that renders without inheriting `app.css` will silently look wrong with no missing-token error.

**Ingestion pipeline — the biggest reuse story (PARTIAL/EXCEEDS, not missing).** A production-grade pipeline and run console already exist and far exceed the mock: SSE live transport, heartbeat strip, per-stage odometers, a trust-score completion ledger, stall/reclaim durable runs, graph-repair panels, rich failure handling — ~2,170 lines in `ConnectIngestRunConsole.svelte`. Mismatches to reconcile, not rebuild: (1) **7 canonical stages** (`extracting·relating·grouping·embedding·validating·remediating·storing`, `packages/connect-core/src/ingest/job-record.ts:7-15`) vs the mock's 4 (Extract·Relate·Group·Embed…), and validation/remediation already run *inside* M1 — blurring the M1/M2 boundary; (2) **a 4-step setup wizard with different steps** (Provider key → Sources → Domain → Review & launch; `pipeline-config.ts:103-145`) handing off to a separate `/runs/[id]` console, not the mock's single Sources→Configure→Running→Done flow; (3) per-stage model choice lives in a separate `/routes/ingestion` area, not an inline Configure disclosure; (4) **no M1-Done "ask your data" step** — completion routes to Claims/quarantine, not an ask box; (5) the **amber "rate-limited, backing off automatically" banner is genuinely missing** as a distinct UI state — the engine auto-backs-off on 429 (`model-call.ts:212-303`) but only logs a `[RETRY]` line; (6) the prototype's **dev-only fault injector has no real counterpart** (the engine surfaces only real errors) — demoing edge states needs a product call. The flagged fail-open cluster (C1/C2/C3) appears **already fixed** in this checkout (`validation.ts:120-124`; `docs/reviews/connect-ingest-failopen-fix.md:45-58`).

**MCP / Connect (HIGH, partly a deliberate reversal).** The handoff wants ONE Connect area merging widget/MCP/REST/SDK/GraphQL with per-connection keys (`01_CONCEPT.md` lesson 4). Reality did the **opposite on purpose** — the Connect hub was dissolved into `/integrations` (Connections = inbound providers), `/agents` (MCP), `/access` (Gateway keys & Routing), with legacy `/connect/*` 308-redirecting to them (`connect/[...legacy]/+page.server.ts:6`). MCP wiring genuinely exists and is reusable (`ConnectAgentSetup.svelte:99` mints a gateway key + a copy-ready `@restormel/mcp` snippet; the AAIF tool registry is at `/agents/catalogs`). Re-merging is a reversal that re-couples three independently-shipped surfaces and invalidates the redirects. **Naming collision risk:** the handoff's "Connections" (outbound apps) vs the live Foundation item literally labelled "Connections" = `/integrations` (inbound providers) (`nav-config.ts:104`).

**Store / M3 (DIVERGENT premise + MISSING choice).** `ConnectGraphStorePanel.svelte` already does engine-pick → read-only verify → save with honest errors (`:504,566,699`) and exceeds the mock's engine list (Surreal/Neo4j/Weaviate/Neptune + one-click workspace-Neon). But: it lives as the **demoted "store" aside** of the ingest wizard (`pipeline-config.ts:143`), not a `/settings/store` destination; the MVP default is **BYO / Neon auto-provisioned**, not a Restormel managed store you *migrate off* — so the handoff's "graph lives in our managed store, moving doesn't move it, you'll decide next" narrative (`07_PROMPTS.md` prompt 8) has no counterpart (`ConnectGraphStorePanel.svelte:493`); and the **"this database isn't empty → use/add/keep-separate" choice does not exist** — there is no emptiness/node-count probe (`graph-target-service.ts:520`), and adding one stretches the literal "read-only, nothing written" guarantee.

## Risks & unknowns

- **Migrating the shipped IA toward the design is deliberate, test-locked work (MEDIUM — was HIGH before the founder steer).** Per the steer the design *supersedes* the shipped "Phase 3 north-star" IA, so this is **intended migration, not an accidental revert** — but it still means rewriting tightly-coupled, test-locked contracts together: `nav-config.test.ts` (the 4 items + 3 groups + topbar titles), `route-manifest.test.ts` (route classification), `legacy-route-redirects.ts` (the 308 map), and the shell layout. A partial edit fails CI in non-obvious places, so sequence it as **one planned IA-migration unit with its tests rewritten in the same change** — not a screen-by-screen drift. Keep the redirect map so existing deep links survive the rename.
- **Live ingestion + run console: a ~2,170-line, invariant-heavy component (HIGH).** It encodes hard-won guards — a 2-mutation-fetch budget, SSE-cursor resume against log loss/duplication, reduced-motion freezing of the heartbeat, a single-source completion ledger — protected by `.live.test.ts` / `.machine-room.test.ts`. Reframe to the new IA must be **wrap/relabel, not rewrite**. Separately, the run console can run in **STUB/preview mode** (`worker-stub.ts:1-8` — "full LLM + graph execution remains in SOPHIA until adapter wiring lands"); if the RES-113 target environment is still stub for some workspaces, the M1 "ask your own data" aha cannot be delivered there. **Confirm full execution is wired before promising the conversion moment.** The known fail-open cluster (`docs/reviews/connect-ingest-context.md:143-160`) is fixed in this checkout, but the fix should be re-verified as part of the RES-113 build.
- **The missing amber rate-limit banner is an honesty gap the design treats as required (MEDIUM).** Surfacing it needs the engine to emit a structured backoff signal through the job record/SSE to the UI — small but cross-cutting (engine → job record → SSE → console).
- **Claim triage mutates graph state via SvelteKit server routes + Postgres/Surreal — mandatory high-risk-security review (MEDIUM).** The triage path (`PATCH /graph/units/{id}/validation`, `/revalidate`) and any M4 key-scope change touch Connect server routes and graph state with session-context auth; per CLAUDE.md these require the `restormel-high-risk-security` review **before** the PR. The triage surface itself is strong and reusable (`ClaimsStampingDesk.svelte`, decision logic in pure `claims-stamping-desk.ts`), but the mock's "live trust climbs 88→97 as you triage" animation **contradicts the shipped model**, which deliberately *defers* the per-stamp trust delta and recomputes only on Home (`claims-stamping-desk.ts:300` — `SESSION_TRUST_DELTA_DEFERRED`). And the EBV accept-guard means you **cannot Accept everything** — `canAcceptAsSupported` disables the Supported stamp for claims with no bound evidence (`evidence-dossier.ts:93`), breaking the mock's "tap A/W/U to clear to 0" flow.
- **Over-claiming "verified" before EBV is wired (HIGH — the exact failure the ADR exists to prevent).** Evidence-Bound Verification is approved but **not wired into ingest** (`docs/decisions/evidence-bound-verification.md`); the validator still judges against a 12k-char source prefix (`validation.ts:16,38`), and the scorecard fail-safes most units to "unverified" (`trust-scorecard-service.ts:94`). A polished trust meter + "production-grade" badge on top of legacy `ok/weak/unsupported` asserts trust the pipeline can't yet substantiate — the falsifiability test (click through to the quote) fails. A faithful M2 will honestly read *mostly unverified*, contradicting the mock's reassuring 88/97. **Decide whether M2 can ship on the structural score, or is blocked on EBV.**
- **Non-destructive DB switch (M3) — provable safety is unbuilt and partly contradictory (MEDIUM).** The "isn't empty → use/add/separate" choice needs to read existing node counts during the "nothing written" step (a read, so safe) but then implies routing future writes into a possibly-shared DB. Getting "no overwrite of customer tables" provably right overlaps the existing additive-only `allow_claim_versions_table` design — there must be **one coherent safety story**, not two. And the panel's default copy/options are flag-gated (`connectNeonGraphStore`); an M3 build that hardcodes the managed-store premise will misstate reality when the flag flips.
- **M4 per-connection keys + enforced access level is a backend change, not a screen (HIGH).** `createApiKey({label})` and `authorizeKnowledgeWorkspaceRequest` have no scope concept; read vs read+write means new key metadata, issuance UI, a gate on `connect.memory.write`, a DB migration, and a security review. Estimating M4 as "recreate the mocks in Svelte" badly understates it.
- **Demo-graph dependency for M0 (MEDIUM).** M0's "cited answer before setup" assumes a queryable demo graph for a fresh workspace pre-ingest. A `seed-demo-graph` service and starter corpus exist (`lib/server/connect/demo-graph/seed-demo-graph.ts`), but whether a graph is provisioned pre-ingest for a brand-new workspace was not verified. The "ask your data" reuse target (`graph-comparison` family) is built for a managed-vs-self *comparison* scenario; whether it answers from an arbitrary just-built graph with citations needs a spike before it's assumed reusable for M1-Done and M0.

## Build-order sanity check (07_PROMPTS.md, prompt-by-prompt)

The handoff's order (`07_PROMPTS.md`, prompts 0–9) is internally sensible but assumes greenfield. Several prompts will **not** map cleanly:

- **Prompt 0 — Recon.** Fine and necessary. Its *result* is this review: the structure has moved on. Keep, but expand its output to "reconcile against the shipped north-star IA," not just "confirm tokens/classes."
- **Prompt 1 — State store + personas.** ⚠️ **Conflicts.** It builds a persisted client `graph.svelte.ts` with `applyEffect` hardcoding demo numbers and a 3-persona model. This duplicates server-truth (`connect-spine.ts:381`) and re-introduces the silent-no-op class (`connect-spine.ts:234`); persona has no real source or inference. **Reorder/replace:** do *not* build a persisted client graph. First do a **mapping spike** — map M0–M4 onto the live spine stages and decide the persona source. Derive position from the existing hub payload.
- **Prompt 2 — Navigation + shell (the IA change).** 🚫 **Blocker as written.** It implements the verb spine and folds Runs→Build, Prove→Home, Agents+Gateway-keys→Connect — i.e. it reverts the shipped north-star IA, the dissolved-Connect decision, and the 308 redirect map (`nav-config.ts:72-77`, `legacy-route-redirects.ts:50`, `route-manifest.test.ts:48`). **Do not run until the gating IA decision is made.** If the journey layers *onto* the north-star IA, this prompt is deleted; if it supersedes, it becomes a deliberate config + test + redirect rewrite, scoped and security-reviewed.
