# ISMS records & incident logging hub (Restormel Keys)

The single routing skill for **every governance / ISMS record-keeping obligation**. Don't rediscover
the templates ad-hoc — match the situation to a row below, then follow the filing process. The records
system already exists; your job is to use it, not reinvent it.

ISMS scope: **Restormel product + supporting infrastructure.** Controller: **Allotment Technology Ltd**
(co. no. 16925574). Solo-founder UK LTD — lean, evidence-based, proportionate to stage.

---

## MANDATORY: after any incident / outage, FILE an incident record

**This is not optional.** The moment a production incident, outage, or alert has been *remediated*,
file an incident record from **REC-TPL-004** → `evidence/incidents/<date>-<slug>.md`. Capture it while
fresh. Severity does not matter — a 10-minute single-endpoint degradation still gets a record (see the
worked example below). An incident handled with no record filed is an ISMS failure, not a clean close.

Worked example (file these exactly like this): **REC-INC-001** =
`evidence/incidents/2026-06-16-catalog-503-missing-migration.md` (filed via PR #66).

## Record-type → template + directory

| Situation | Template | File the copy to | id prefix |
|-----------|----------|------------------|-----------|
| Incident / outage / alert remediated | `evidence/templates/incident.md` (REC-TPL-004) | `evidence/incidents/<date>-<slug>.md` | REC-INC-* |
| High-risk processing activity | `evidence/templates/dpia.md` (REC-TPL-003) | `evidence/dpia/<name>.md` | REC-EVID-* |
| Quarterly access review | `evidence/templates/access-review.md` (REC-TPL-001) | `evidence/access-reviews/<YYYY-QN>-access-review.md` | REC-EVID-* |
| ISMS posture / audit report | `evidence/templates/posture-report.md` (REC-TPL-002) | `evidence/posture/<date>-posture.md` | REC-EVID-* |
| Small one-line event not worth a file | — | append a line to `evidence/ledger.jsonl` (append-only) | — |

`evidence/dpia/` and `evidence/access-reviews/` are created on first use. Posture reports are normally
generated by the **Phase 6 evidence agent** (`records-posture.yml`, Mondays 08:00 UTC) — only hand-write
one if asked.

## Not an evidence record? → governance document to update

Some obligations update a living **Tier-2 governance document** (`governance/`) instead of (or as well as)
filing evidence. These are the **event-triggered updates** — stage them in the SAME turn as the event:

| Event | Update |
|-------|--------|
| New / removed sub-processor, tool, or connector | `governance/suppliers.yaml` + `ropa.yaml` (+ privacy notice). The `notify-subprocessor-change.mjs` notifier fires on `suppliers.yaml` changes to main (Art 28). |
| New data category or processing activity | `governance/data-inventory.yaml` + `ropa.yaml` |
| Infra change (new host, region, domain) | `governance/asset-inventory.yaml` + `suppliers.yaml` |
| Security incident (any severity) | `governance/risk-register.yaml` (+ file the incident record above) |
| New person / contractor / third-party access | `governance/access-control-policy.md` + `asset-inventory.yaml` |
| Cyber Essentials control change (MFA, firewall, patching, host config) | `governance/ce-control-mapping.md` + `cyber-security-policy.md` + `soa.md` |
| Policy review or review-cadence due | the relevant `governance/*.md` policy (REC-POL-*) |
| ISO 27001 SoA / applicability question | `governance/soa.md` (REC-GOV-004) |

Governance homes: `governance/` (policies, `soa.md`, `risk-register.yaml`, `ropa.yaml`, `suppliers.yaml`,
asset/data inventories, `ce-control-mapping.md`), `docs/governance/`, `records/` (the `SCHEMA.md` +
`register.yaml`), `evidence/`. Full event-trigger matrix and review cadence: `governance/README.md`.

## Frontmatter norm (records/SCHEMA.md is the source of truth)

Every managed record carries YAML front-matter:

```yaml
id:              # REC-<TYPE>-<NNN>, zero-padded, stable, never reused
title:           # human-readable
class:           # technical | decision | planning | governance | evidence | legal | people
owner:           # must match a CODEOWNERS entry (a person/handle)
status:          # draft | approved | deprecated | superseded   (incidents: closed once done)
classification:  # public | internal | confidential | restricted
control-tier:    # 0 | 1 | 2 | 3
created:         # YYYY-MM-DD
last-reviewed:   # YYYY-MM-DD
review-interval: # ISO 8601 duration, e.g. P12M — CI computes next-review = last-reviewed + interval
```

**Tier ≥ 2 additionally REQUIRES** `owner`, `approved-by`, `approved-on`, `retention`. Missing any of
these on a Tier-2/3 record is a hard error once enforcement flips on.

- **`classification`** does triple duty: ISO access-control attribute, the per-document ACL, AND the
  publish gate (only `public` ever renders to the public site). Default new evidence to `internal`.
- **`retention`** is a controlled vocabulary, not free text: `P<dur>` / `P<dur>-after-<superseded|no-longer-in-force|processing-ends>` / `life-of-processing` / `permanent` / `review-only`. Incidents use `P6Y`.
- **Control tiers:** 0 ephemeral · 1 managed (CI advisory) · 2 governed (policies/registers, required fields, CI blocking) · 3 evidence (access reviews, posture, incidents, ledger — append-only, CI blocking).

## Filing process (evidence is APPEND-ONLY)

1. **Copy** the matching template — don't edit the template itself.
2. Save the copy to the correct `evidence/<subdir>/` as `<date>-<slug>.md` (or the naming shown above).
3. **Change the front-matter** to the Tier-3 evidence values: `class: evidence`, `control-tier: 3`, and
   set `owner`, `approved-by`, `approved-on`, `retention` (Tier-3 requires them).
4. Fill it in **while the facts are fresh** (detected/impact/response/root-cause/follow-ups for incidents).
5. **Ship via PR / the relay** — never silently hand-edit an approved or filed record. A filed evidence
   record is **append-only / immutable intent**: write once, never silently rewrite; disposition is
   deliberate and logged, never a `git rm`. `records-governance` is **advisory** (warn-only today), so the
   PR + founder merge is the review gate.
6. Binaries (signed PDFs, exported reports) can't carry front-matter → use Forgejo LFS plus a sidecar
   `<file>.meta.yaml` carrying the same fields.

**Do NOT mint a new `REC-*` id by hand-editing the register** — the register (`records/register.yaml`) is
**generated** from source by `scripts/records/register.mjs`. A skill is not a record; filing a record is.

## Self-maintaining-records norm

Records keep themselves current — updating them is **part of the work, not a separate chore**. When any
agent takes an action that introduces or changes a managed fact (a new asset, sub-processor/connector,
data flow, capability, decision, or a material change to one), **stage the matching register/document
update in the SAME turn, without waiting to be asked**. Identify *every* affected register, not just the
obvious one. If unsure which record applies, **flag it rather than skip it**. Anything derivable from
source is generated, not hand-maintained. The Phase 6 evidence agent is the safety net that flags drift.

## Validators & gates to expect

Dependency-free `node` scripts under `scripts/records/`, run by `.forgejo/workflows/records-governance.yml`
(push/PR, **warn-only** today; tier-2/3 flips blocking when `RECORDS_ENFORCE=1`):

- `frontmatter-validate.mjs` — vocab + tier range; tier ≥ 2 missing required fields.
- `freshness-check.mjs` — `last-reviewed` + `review-interval` → next-review; warns at T-30; tier ≥ 2
  overdue is an error when enforced.
- `register.mjs --check` — register matches source · `ledger-append-guard.mjs` — ledger lines immutable ·
  `codeowners-check.mjs` — owner coverage · `mirror-verify.mjs` — mirror discipline.
- `records-posture.yml` — scheduled evidence agent: writes the dated posture report + opens issues for
  overdue/incomplete Tier-2 (origin only, never the GitHub mirror).

After filing, confirm `node scripts/records/frontmatter-validate.mjs` passes for your new record.
